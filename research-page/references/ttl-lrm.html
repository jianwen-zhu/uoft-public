TTL Language Reference Manual

Version 0.1

Status and normative language

This document defines TTL as the normative post-elaboration form of YTL: a finite, typed tensor dataflow language. It specifies the complete textual syntax, static constraints, and execution semantics of this version.

TTL uses a strict syntactic subset of YTL as defined by the YTL Language Reference Manual. Its semantics are the official image of YTL elaboration. Source imports and declarations have already been resolved; they are not copied into TTL text.

The key words MUST, MUST NOT, REQUIRED, SHALL, SHALL NOT, SHOULD, SHOULD NOT, MAY, and OPTIONAL are to be interpreted as described by RFC 2119 and RFC 8174 when, and only when, they appear in bold.

Anything not admitted by the grammar and constraints in this document is not TTL 0.1. In particular, TTL has no implicit operations and no implementation-defined source behavior.

1. Scope

A TTL module describes one or more exported, immutable tensor dataflow graphs. It contains:

  • fully typed tensor parameters and results;
  • a finite, topologically ordered sequence of tensor bindings;
  • direct references to scalar targets used by tensor maps and reductions; and
  • the tensor operations @einsum, @gather, @rearrange, and static subviews.

TTL defines logical tensor values. It does not define storage layouts, buffer allocation, address arithmetic, kernel boundaries, scheduling, device placement, host APIs, checkpoint formats, or program packaging.

TTL 0.1 has no non-export function declarations, ordinary function calls, overload resolution, structural parameters, recursion, loops, conditional expressions, nested let, mutable state, tuple values, tensor literals, implicit broadcasting, or implicit primitive selection.

2. Lexical structure

2.1 Source text

Source text is Unicode, but every token defined by this version is ASCII. Whitespace separates tokens and is otherwise insignificant.

Two comment forms are recognized:

// comment through the end of the line
/* non-nesting block comment */

An unterminated block comment is invalid.

2.2 Tokens

The following regular expressions use conventional notation:

id       ::= /[A-Za-z_][A-Za-z0-9_]*/ ;
integer  ::= /0|[1-9][0-9]*/ ;
float    ::= /([0-9]+\.[0-9]*|\.[0-9]+)([eE][+-]?[0-9]+)?/
           | /[0-9]+[eE][+-]?[0-9]+/ ;
axis     ::= id ;
dyn-axis ::= "$" id ;
target   ::= "@" id ;
core-id  ::= "%" integer ;

Leading zeroes are not permitted on a multi-digit integer. A negative number is the token - followed by an unsigned numeric literal; it is not one token.

The reserved words used by TTL are:

function  export  let  in  map  reduce  true  false

3. Complete grammar

The grammar below is the complete TTL 0.1 grammar. X?, X*, and X+ mean optional, zero-or-more, and one-or-more respectively; X | Y denotes alternatives. Literal punctuation is quoted.

module    ::= export+ EOF ;
export    ::= "export" "function" id "(" params? ")"
              "->" results "=" body ";" ;
params    ::= param ("," param)* ;
param     ::= id ":" type ;
results   ::= type | "(" type ("," type)+ ")" ;

body      ::= refs | "let" binding (";" binding)* "in" refs ;
binding   ::= value-name "=" rhs ;
rhs       ::= signed-literal | value-name selector | primitive ;
refs      ::= value-name
            | "(" value-name ("," value-name)+ ")" | "(" refs ")" ;

primitive ::= target "[" specification "]" "(" operands ")" clause* ;
specification ::= pattern ("," pattern)* "->" pattern ;
pattern   ::= term* ;
term      ::= axis-name | axis-name "=" "(" factor+ ")" ;
factor    ::= axis-name ("=" positive-integer)? ;
operands  ::= value-name ("," value-name)* ;
clause    ::= ("map" | "reduce") "=" target ;

selector  ::= "[" selection ("," selection)* "]" ;
selection ::= axis "=" integer (":" integer)? ;
type      ::= dtype ("[" dimension* "]")? ;
dimension ::= axis "=" positive-integer | dyn-axis ;
dtype     ::= id ;
axis-name ::= axis | dyn-axis ;
value-name ::= id | core-id ;

signed-literal   ::= literal | "-" numeric-literal ;
literal          ::= integer | float | "true" | "false" ;
numeric-literal  ::= integer | float ;
positive-integer ::= integer ;

positive-integer is additionally constrained to the inclusive range 1..2147483647. Empty patterns are meaningful for rank-zero tensors. For example, a scalar-to-scalar map has the specification @einsum[ ->](x).

This grammar is intentionally shorter than the YTL grammar: it adds no syntax to YTL and removes every construct that elaboration has resolved. In particular, a TTL module cannot declare a helper, reducer, or target.

The subset correspondence is normative:

TTL production Restriction of YTL production
module, export program and function, with zero imports
body, binding, rhs, refs expr, binding, prefix, and atom
primitive, specification, pattern, term, factor, clause the same primitive productions; TTL clauses restrict reference to target
selector, selection the same selector productions with resolved integer expressions and static axes
type, dimension, dtype the same open nominal dtype production, with complete TTL extents

Accordingly, every sentence derived by the TTL grammar MUST also be derivable by the YTL grammar. TTL restrictions may remove alternatives or replace a YTL expr by a literal or identifier, but they MUST NOT introduce a token, delimiter, ordering, or call envelope absent from YTL.

4. Module structure and namespaces

  1. A module MUST NOT contain an import. Import selection is a source-level operation completed before TTL is emitted.
  2. A module MUST contain one or more exported function definitions.
  3. It MUST NOT contain any other declaration or definition.
  4. Export names MUST be unique within the module.
  5. Tensor parameter names MUST be unique within an export.
  6. Tensor binding names MUST be unique within an export and MUST NOT shadow tensor parameters.
  7. Tensor names in different exports are independent.
  8. Target names beginning with @ occupy a fixed namespace and cannot be declared by a module.

%N is an elaborator-generated value name, analogous to a numbered SSA value. It may name a TTL binding and may be referenced anywhere an earlier binding name is accepted. Parameters and exports retain human identifiers. A producer may use %N when no useful source name remains; ordinary identifiers have the same binding semantics.

Every tensor operand in a binding MUST name a tensor parameter or an earlier binding. Every result reference MUST name a tensor parameter or a binding. These rules make the tensor graph finite and topologically ordered.

5. Types and abstract tensor values

5.1 Element types

TTL preserves the complete nominal dtype of every elaborated YTL value. Its dtype grammar is deliberately open and is exactly the YTL dtype grammar. The mandatory ttl.lang target environment defines these portable baseline types:

Type Meaning
bool Boolean false or true
i32 signed two's-complement integer in [-2^31, 2^31-1]
f16 IEEE-754 binary16 value
f32 IEEE-754 binary32 value
f8e4m3fn finite E4M3 value defined by the YTL LRM
f4e2m1 E2M1 value defined by the YTL LRM

There is no implicit conversion between element types.

A target environment MAY add nominal dtypes. It MUST define each added type's value domain and canonicalization. TTL structural operations preserve such types without interpreting their scalar representation.

Integer literals have type i32. Floating literals have type f32. Boolean literals have type bool. Consequently, TTL 0.1 has no textual f16 literal.

5.2 Tensor types

A tensor type consists of an element type and an ordered list of distinct named dimensions. A type with no dimensions is a rank-zero tensor, also called a scalar tensor.

f32                         scalar
f32[row=4 column=8]         dense rank-two tensor
f32[batch=2 $token hidden=64] segmented rank-three tensor

A static dimension is written name=N, where N is a positive i32 literal. A dynamic dimension is written $name and has no type-level extent. Every dimension name MUST occur at most once in one tensor type.

Axis names are semantic. Reordering two dimensions changes the type even when their extents agree.

5.3 Dynamic dimensions

Let a tensor have axes A = (a0, ..., an-1). For each dynamic axis ak, the tensor carries an abstract segment-length function:

L_ak : Coord(a0, ..., ak-1) -> non-negative integer

The function is indexed by the complete coordinate prefix preceding the dynamic axis. It is part of the logical tensor value, not a prescribed storage format.

The coordinate set of a tensor is defined recursively. Begin with the singleton prefix (). For each axis from left to right:

  • if the axis is static with extent N, extend every current prefix with 0, ..., N-1;
  • if the axis is dynamic, extend a prefix p with 0, ..., L_axis(p)-1.

A tensor value is a total mapping from this coordinate set to values of its element type. Empty dynamic segments are legal, including empty segments below another dynamic axis.

5.4 Static extent agreement

When an operation aligns two occurrences of the same static axis name, their extents MUST be equal. Equality of extents does not align differently named axes.

5.5 Dynamic descriptor compatibility

Two occurrences of the same dynamic axis name denote compatible logical segments subject to these rules:

  1. If both descriptors have the same prefix axes, their lengths MUST agree at every prefix coordinate.
  2. If one descriptor's prefix axes are an ordered subset of the other's, the less-specific length is a capacity and MUST be at least the corresponding more-specific length.
  3. In a result domain containing both prefix sets, a less-specific descriptor is projected to each refined prefix.
  4. Compatible candidates derive the result length by their pointwise minimum.
  5. A result dynamic axis MUST have at least one input descriptor whose complete prefix can be projected from the result prefix.

Descriptors with incomparable prefix dependencies may participate only when an operation forms a result prefix containing both dependencies. The pointwise rule then defines their joint domain.

All exported arguments MUST satisfy these compatibility rules before any binding is evaluated. Every binding applies the same rules to its operands.

6. Primitive target references

An @einsum map or reduce clause refers directly to one operation in the target environment defined in Section 8. It cannot name a user-defined function. A map target receives one scalar from each tensor operand, in operand order. Its signature MUST match those element types exactly.

A reduce target receives the accumulator and next mapped value. It MUST be registered as a reducer by the target environment. Its identity and ordering contract come from that environment; they are not repeated or overridden in TTL text.

Elaboration splits a compound scalar expression into target-atomic tensor bindings. Consequently every TTL map and reduction performs at most one scalar target operation.

7. Tensor dataflow

7.1 Parameters and bindings

Exported parameters are the input nodes of the dataflow graph. TTL does not classify them as weights, activations, constants, state, or invocation data.

Bindings are evaluated in textual order. Every binding produces one immutable tensor value. A binding has no explicit type annotation; its type is uniquely determined by its literal or primitive and MUST satisfy all rules below.

7.2 Scalar constants

A binding whose right-hand side is a literal produces a rank-zero tensor of the literal's lexical type. Negative numeric literals retain the unsigned literal's type.

TTL 0.1 has no non-scalar tensor literal.

7.3 Results

The export result signature contains one or more complete tensor types. The result expression contains the same number of references in the same order. Each referenced tensor's inferred type MUST exactly equal the corresponding declared result type.

Multiple results are multiple graph edges. They do not create a tuple tensor or a tuple-typed runtime value.

8. Target environment

A target name is self-identifying syntax: it begins with @. TTL neither imports nor declares targets. A TTL consumer supplies a target environment when it verifies, executes, or lowers a module.

Every TTL target environment MUST implement the complete ttl.lang ABI defined by the YTL LRM. It MAY provide additional targets and dtypes.

For every referenced target, the environment MUST provide:

  • its ordered input element types and result element type; and
  • deterministic scalar semantics over its stated domain; and
  • any non-default dynamic-descriptor rule required by that scalar operation.

The default descriptor rule is ordinary pointwise compatibility across the mapped operands. A value-selection target identifies which operands are the alternatives; those alternatives define one equal result domain, while the condition may broadcast over but cannot select that domain.

A target admitted as a reducer MUST additionally provide one typed scalar literal identity and one contract: left_ordered, reassociative, or associative. No contract permits permutation of reduction leaves. Target results are rounded once to their declared result type.

A module is well formed only relative to a target environment containing every target it references. The elaborator and consumer MUST use environments with identical signatures, scalar semantics, reducer identities, and contracts for those names. A target-domain violation is a dynamic execution error.

Target environments are interfaces to a TTL consumer, not module imports and not additions to the TTL grammar. A consumer may define a profile requiring a particular environment; such a profile does not change TTL.

9. @einsum

9.1 Form and static constraints

An @einsum has one input pattern per tensor operand followed by one result pattern.

  1. It MUST have at least one operand.
  2. Every pattern term MUST be a bare axis name.
  3. Input pattern i MUST exactly equal operand i's ordered axes.
  4. The result pattern MUST NOT contain duplicate axes.
  5. Every result axis MUST occur in at least one input pattern.
  6. Static extents of aligned axes MUST agree.
  7. If present, map MUST name a compatible target in the target environment. If absent, @einsum MUST have one operand and maps it identically.
  8. A reduce clause is REQUIRED exactly when at least one iteration axis is absent from the result, and forbidden otherwise.

There is no implicit multiplication or addition in TTL.

9.2 Iteration axes and projections

The iteration-axis list is the ordered union of input axes: visit operands from left to right and each operand's axes from left to right, retaining the first occurrence of each name.

Each operand projection selects from an iteration coordinate the positions named by that operand's pattern, in pattern order. An operand missing an iteration axis is broadcast across that axis. This broadcast is explicit in the patterns; it is not inferred from trailing positions or equal extents.

The reduced axes are the iteration axes absent from the result pattern, in iteration order.

9.3 Non-reducing map

When there are no reduced axes, @einsum is a regular named-axis map. For each result coordinate:

  1. project the coordinate into each operand;
  2. read one scalar from each operand;
  3. apply the map target, or read the sole operand unchanged; and
  4. store the mapped scalar at that result coordinate.

The result element type is the map target's result type, or the sole operand's type for identity mapping.

If the target environment marks a map operation as value selection, its two alternative operands define the result dynamic descriptor and MUST have equal segment lengths at every result prefix. The Boolean condition may be less specific only when it covers the complete alternative domain. A condition cannot select a result shape.

9.4 Reduction

When reduced axes exist, iteration coordinates are enumerated lexicographically in iteration-axis order, with each coordinate increasing from zero. For each result coordinate, mapped values whose projected result coordinate is equal form one ordered reduction group.

Every valid result coordinate has a group, even when its reduced domain is empty. Evaluation initializes the accumulator to the reducer identity and then applies:

accumulator := reduce_target(accumulator, mapped_value)

for the group's mapped values in order. An empty group therefore produces the identity.

The reducer target input type MUST equal the map result type. The @einsum result element type is the reducer result type.

9.5 Dynamic result domain

The result's dynamic descriptors are derived by the compatibility and pointwise rules in Section 5.5. Every result dynamic axis must retain enough of its source prefix to project at least one descriptor. Dropping a varying prefix while retaining its dynamic axis is invalid.

10. @gather

10.1 Form

@gather[source-axis -> inserted-axes](data, indices)

data may have any TTL element type. indices MUST have element type i32. The source side MUST name exactly one axis of data.

Let R be the ordered data axes after removing the source axis. The inserted axes MUST be exactly the index axes that do not occur in R, in index-axis order. Every other index axis is a shared axis and MUST occur in R with a compatible extent or dynamic descriptor.

The result axes are formed from the data axes by replacing the source axis with the inserted axes. Shared index axes retain their positions from data. The result element type is the data element type.

10.2 Evaluation

For each result coordinate:

  1. project the coordinate onto the index axes and read integer j;
  2. construct a data coordinate from the result's remaining data axes and set the source-axis coordinate to j; and
  3. read that data element into the result coordinate.

j MUST be non-negative and inside the source-axis domain at that complete data prefix. Otherwise evaluation fails with an out-of-bounds error.

Dynamic result axes are derived from aligned data and index descriptors. A gather into a segmented suffix additionally checks the selected data coordinate against that suffix's per-prefix segment lengths.

11. Static subviews

11.1 Form and constraints

A subview selects one or more distinct static axes of an earlier tensor:

x[layer=1]
x[row=1:3, column=0]

Every selected axis MUST exist in the source and MUST be static.

For an index selection axis=i with source extent N:

0 <= i < N

The selected axis is removed from the result.

For a range selection axis=begin:end:

0 <= begin < end <= N

The axis remains in the result with extent end - begin.

Unselected axes retain their order, kind, and extent. The result element type equals the source element type.

11.2 Evaluation

An index selection fixes the source coordinate to i. A range selection maps result coordinate r to source coordinate r + begin. Multiple selections are applied simultaneously.

Selecting and dropping a static axis before a dynamic axis specializes the dynamic descriptor to the selected prefix. Range selection restricts and renumbers the corresponding prefix coordinates. This is permitted even though the resulting dynamic axis has fewer prefix axes.

12. Single-source @rearrange

12.1 Purpose

A single-source @rearrange defines a value-independent bijective index map using permutation, static split/merge, extent-preserving rename, and insertion of statically known extent-one logical axes.

It never inspects or combines element values.

12.2 Patterns

The physical axis names of the input pattern MUST exactly equal the source tensor's ordered axes. The physical axis names of the output pattern define the result axes and MUST be unique.

A bare term a introduces logical axis a. A composite term physical=(a b ... z) says that the physical axis is the row-major product of the listed logical factors, with the last factor varying fastest.

A static factor's first occurrence MUST carry its resolved extent unless that extent is already established by an earlier bare input term. Thus TTL may write group=(high=2 low=2). Later occurrences of high and low may omit the annotations. Repeated annotations MUST agree. A dynamic factor MUST NOT carry an extent. These annotations make every rearrange self-contained; no external axis environment participates in TTL typing.

Every input physical extent MUST equal the product of its logical factor extents. Factor extents must be uniquely determined from input extents and the complete result type. A logical name absent from the input is permitted only when its result extent is one.

Every non-unit logical input axis MUST occur exactly once in the output. Every non-unit logical output axis MUST occur exactly once in the input. Dropping, duplicating, or repeating a non-unit logical coordinate is forbidden.

12.3 Dynamic restriction

A dynamic physical axis may occur only as an unfactored bare term or as the sole factor of a dynamic result term. TTL 0.1 cannot split, merge, or factor a dynamic dimension. Any renamed dynamic result axis MUST also begin with $.

The rearrangement must induce a valid complete-prefix segment function for every output dynamic axis. No physical descriptor encoding is prescribed.

12.4 Coordinate map

Splitting physical coordinate p into factors with extents (N0, ..., Nk-1) uses mixed-radix row-major coordinates:

ik = p mod Nk
p  = p div Nk

applied from the last factor to the first. Merging factor coordinates uses:

p = (((i0 * N1 + i1) * N2 + i2) ...)

The output value at the resulting coordinate is the source value at the original coordinate. The map MUST produce each result coordinate exactly once.

13. Multi-source @rearrange

13.1 Static constraints

With two or more operands, @rearrange is ordered composition along one axis.

  1. Every input and output term MUST be bare.
  2. There MUST be one input pattern per operand.
  3. Every input pattern MUST exactly match its operand axes.
  4. All inputs and the output MUST have equal rank.
  5. All operands MUST have one element type.
  6. Exactly one axis position is the composition position.
  7. At least one input must rename that position relative to the output, making the position explicit.
  8. Every non-composition position MUST have the same axis name, static extent, and dynamic descriptor domain in every input and the output.

If all source composition axes are static, a static result extent is their sum. If any source composition axis is dynamic, the result composition axis MUST be dynamic. A dynamic result axis may also compose static source axes, producing equal segment lengths at each valid prefix.

13.2 Evaluation

For each complete prefix preceding the composition position, source segments are concatenated in operand order. A source coordinate i from operand k maps to:

i + sum(length of operand j at this prefix, for 0 <= j < k)

All other coordinates are unchanged. Empty source segments are legal. For a dynamic result, its per-prefix length is the sum of source lengths at that prefix.

14. Evaluation and errors

14.1 Invocation

An invocation supplies exactly one tensor value for every exported parameter. Each value's element type, ordered axes, static extents, and dynamic prefix structure MUST match its parameter type. Extra or missing arguments are invalid.

14.2 Evaluation order

Bindings are evaluated in textual order. Scalar target arguments are evaluated left to right. Tensor coordinates are enumerated lexicographically in their declared axis order. Reduction order is additionally constrained by its reducer contract.

Because tensor values are immutable and tensor bindings have no side effects, an implementation may use a different execution order only when it preserves the numerical permissions of the declared scalar and reduction contracts.

14.3 Rounding

An f16 or f32 input element is rounded to its declared format when the tensor value is formed. Each scalar target result is rounded to its declared format. i32 operations and conversions reject values outside the signed 32-bit range.

14.4 Dynamic errors

A statically well-formed program may still fail at invocation or evaluation for:

  • an argument that does not match its declared tensor type;
  • incompatible segment lengths for a repeated dynamic axis;
  • a missing dynamic descriptor for a required result prefix;
  • a gather index outside its selected source domain;
  • a scalar target operand outside the defined numerical domain; or
  • a rearrange whose runtime dynamic coordinate map is not total and one-to-one.

Such conditions MUST be reported as errors. Silent truncation, padding, wrapping, clamping, or undefined behavior is forbidden.

15. Static well-formedness checklist

A TTL 0.1 module is well formed only if all of the following hold:

  1. It satisfies the complete grammar in Section 3.
  2. It has no imports, one or more exports, and no other declarations.
  3. Every type is complete and uses a valid nominal dtype and dimensions.
  4. Names are unique in their required namespaces.
  5. Every tensor operand is a parameter or earlier binding.
  6. Every map and reduce clause directly names a compatible operation in the supplied target environment.
  7. Every reducer target uses its target-environment identity and contract.
  8. Every tensor primitive has its exact arity, patterns, clauses, and result type.
  9. Every static axis alignment has equal extents.
  10. Every dynamic result descriptor is derivable from its operands or the explicit subview/rearrange mapping.
  11. Every binding has one uniquely inferred tensor type.
  12. Result-reference arity and types exactly match the export signature.
  13. Every export's dataflow graph is finite and topologically ordered.

16. Complete examples

The examples that name @multiply_f32 and @add_f32 assume a target environment providing the signatures and semantics suggested by those names. The other examples require no scalar targets.

16.1 Dense linear projection

export function linear(
    x: f32[row=2 shared=3],
    weight: f32[shared=3 column=4]
) -> f32[row=2 column=4] =
    let
        %2 = @einsum[
            row shared,
            shared column
            -> row column
        ](x, weight) map=@multiply_f32 reduce=@add_f32
    in
        %2;

export function identity(
    x: f32[row=2 shared=3]
) -> f32[row=2 shared=3] = x;

The first binding maps @multiply_f32 and reduces shared with the target environment's @add_f32 identity and order in one einsum. The second export shows that a TTL module may carry several independent entry points.

16.2 Dynamic ordered composition

export function append(
    past: f32[batch=2 $past channel=4],
    step: f32[batch=2 $step channel=4]
) -> f32[batch=2 $source channel=4] =
    let
        %2 = @rearrange[
            batch $past channel,
            batch $step channel
            -> batch $source channel
        ](past, step)
    in
        %2;

For each batch coordinate, $source is the ordered concatenation of that batch's $past and $step segments. Different batches may have different lengths, and either source segment may be empty.

16.3 Gather and subview

export function lookup_layer(
    tables: f32[layer=2 vocabulary=5 channel=3],
    ids: i32[batch=2 token=4]
) -> f32[batch=2 token=4 channel=3] =
    let
        %2 = tables[layer=1];
        %3 = @gather[vocabulary -> batch token](%2, ids)
    in
        %3;

The subview removes layer; gather then replaces vocabulary with the two index axes batch token.

16.4 Self-contained factorization

export function split_hidden(
    x: f32[hidden=8]
) -> f32[head=2 channel=4] =
    let
        %1 = @rearrange[
            hidden=(head=2 channel=4)
            -> head channel
        ](x)
    in
        %1;

The factor annotations make the split uniquely recoverable from this module. No external declaration of head or channel is required.
