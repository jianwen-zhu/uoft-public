YTL Language Reference Manual 1.0

Version 1.0 compatibility profile

Status

This document is the normative definition of the YTL 1.0 compatibility profile. It does not reinterpret artifacts governed by the earlier YTL 0.1 manual.

YTL 1.0 is intentionally defined from the common YTL 2.0 grammar and semantics so that it is a strict source-syntax subset of YTL 2.0 rather than a language that YTL 2.0 must later reinterpret. The common rules are specified by the YTL 2.0 specification. This profile states the exact 1.0 restrictions and version relationship.

The version relation is monotonic. A later language version MUST preserve every program admitted by the preceding stable version, with the same static meaning and reference result, while adding at least one new program. The same rule applies independently to TTL.

The key words MUST, MUST NOT, REQUIRED, SHALL, SHALL NOT, SHOULD, SHOULD NOT, MAY, and OPTIONAL are to be interpreted as described by RFC 2119 and RFC 8174 when, and only when, they appear in bold.

1. Language contents

YTL 1.0 includes the following foundations from the YTL 2.0 specification. The language names and related work are discussed in Appendix B of that manual.

  • module declarations for nominal concrete axis identities;
  • static parameters that become generic axes when used in axis positions;
  • order-free semantic tensor types with name-based alignment and broadcasting;
  • RHS-derived expression types;
  • static axes and a dynamic-axis dependency partial order;
  • immutable module-scope globals with module-instance lifetime;
  • ordinary and structurally recursive first-order functions;
  • scalar lifting and explicit @einsum map and invariant reduction;
  • gather, functional scatter-reduce, and selectors;
  • value-independent @rearrange, including explicit static replication;
  • the ttl.lang scalar vocabulary; and
  • elaboration to fully typed, primitive-only TTL 1.0.

Optional vocabulary entries may add nominal dtypes and scalar operations without changing YTL syntax. In particular, the reference ttl.lang module retains optional low-precision conversions for quantized-model compatibility.

YTL 1.0 does not include:

  • scoped let prefixes;
  • fibre-selection or prefix-lifting surface syntax; or
  • the APL-style infix reducer.mapper[axes] expression.

The absence of infix map-reduce does not remove tensor mapping or reduction. YTL 1.0 expresses them through explicit @einsum patterns and map= and reduce= clauses.

2. Exact syntax restriction

YTL 1.0 is the common grammar in Section 2.2 of the YTL 2.0 manual. It omits the two additions isolated in Section 2.3: scope-expr and map-reduce-op. Its expression productions are therefore:

expr       ::= let-expr | if-expr | infix-expr ;
infix-expr ::= prefix (binary-op prefix)* ;

All other lexical and grammar productions are exactly the common productions in Section 2.2 of the YTL 2.0 specification.

These expressions witness strict inclusion:

// YTL 2.0 only: scoped lifting
let [copy := 2] in x

// YTL 2.0 only: APL-style infix map-reduce
A +.*[shared] B

Neither expression is valid YTL 1.0. There are no additional YTL 1.0 forms absent from YTL 2.0.

3. Semantic compatibility

Every construct shared by YTL 1.0 and YTL 2.0 has exactly the same:

  • name resolution;
  • nominal axis identity;
  • generic-axis substitution;
  • tensor type and extent inference;
  • dynamic descriptor behavior;
  • overload selection;
  • primitive typing;
  • invariant-reduction semantics;
  • reference evaluation; and
  • error conditions.

In both profiles, a module axis declaration introduces a concrete identity, and a static parameter in a function header becomes a generic axis when used in an axis position. Calls specialize those generics explicitly. YTL 2.0 therefore does not reinterpret a YTL 1.0 function signature or call.

For every valid YTL 1.0 program p:

parse_2.0(p) succeeds
type_1.0(p) = type_2.0(p)
evaluate_1.0(p) = evaluate_2.0(p)
elaborate_1.0(p) ~= elaborate_2.0(p)

Elaboration equivalence above is structural equivalence as defined by the YTL 2.0 LRM. It ignores generated binding names and the written order of unordered axis sets; it preserves every semantically ordered operand or result edge.

4. Common TTL

YTL 1.0 and YTL 2.0 elaborate to the language defined by the TTL 1.0 specification. Its complete grammar is obtained only by restricting the common YTL grammar: axes and extents are concrete, functions are exports, types are complete, and expressions are flat primitive dataflow. TTL adds no syntax to either YTL profile.

YTL 2.0 scope flattening and infix map-reduce introduce no new TTL form:

YTL 1.0 source ────────────────┐
                               ├──> TTL 1.0
YTL 2.0 source ── flatten ─────┘

TTL 0.1 artifacts remain governed by the released TTL 0.1 manual. The TTL 1.0 manual makes no unsupported monotonic-compatibility claim while axis ordering, dynamic dependencies, and reduction invariance differ between the two versions.

5. Required compatibility evidence

Conforming implementations MUST provide the following compatibility evidence:

  1. every positive YTL 1.0 syntax fixture MUST parse in YTL 2.0 mode;
  2. every YTL 2.0-only scope and infix fixture MUST be rejected in YTL 1.0 mode for the stated profile restriction rather than a downstream error;
  3. shared source fixtures MUST receive identical types and diagnostics;
  4. elaboration of every YTL 1.0 fixture MUST produce structurally equivalent TTL graphs in both modes; and
  5. both modes MUST emit TTL accepted by one TTL 1.0 verifier;
  6. elaboration MUST preserve module globals as direct TTL declarations and references without changing export parameter lists;
  7. emitted dynamic-axis dependencies MUST satisfy contextual well-formedness and survive elaboration; and
  8. every approximate reducer emitted to TTL MUST have an order-invariant admissibility predicate in the paired target environment.

Until this evidence exists, this file is a compatibility design contract, not a conformance claim.
