TTL Language Reference Manual 1.0

Jianwen Zhu

Version 1.0

Status and normative language

This document is the normative definition of TTL 1.0, implemented by the accompanying reference parser, verifier, and interpreter. It does not reinterpret artifacts governed by the earlier TTL 0.1 manual.

TTL, the Tiny Tensor Language, is a flat, fully typed, primitive-only language intended as a compact interchange between tensor frontends, interpreters, and lowering compilers. This manual defines TTL without requiring knowledge of any source language.

The key words MUST, MUST NOT, REQUIRED, SHALL, SHALL NOT, SHOULD, SHOULD NOT, MAY, and OPTIONAL are to be interpreted as described by RFC 2119 and RFC 8174 when, and only when, they appear in bold. In brief, MUST and REQUIRED state conformance requirements, MUST NOT states a prohibition, SHOULD states a recommendation that requires a documented reason to disregard, and MAY marks an allowed choice.

1. Overview

TTL describes the mathematical dataflow of a tensor computation after all source-level composition has been completed. A producer emits TTL. A consumer parses and checks that TTL and may interpret it or lower it to another representation. One possible producer is an elaborator, a frontend phase that replaces higher-level source constructs with explicit TTL.

TTL assumes no particular source language. It is itself a small programming language with the following abstract objects:

  • An element type, or dtype, describes one scalar element, such as f32.
  • An axis names one independent coordinate dimension. Its identity and its extent are separate properties.
  • An axis domain is the set of valid coordinates for one axis occurrence.
  • A tensor maps every valid combination of its named coordinates to one element. Its rank is its number of axes; a rank-zero tensor is a scalar.
  • A tensor type gives a dtype and a finite set of named axis domains.
  • A value is an immutable scalar or tensor.
  • A module is one TTL source unit containing axis declarations, globals, and exports.
  • A global is an immutable module input shared by all invocations of the module's exports.
  • An export is an externally callable function. Its parameters and globals are input nodes, its bindings are computation nodes, and its result references are output edges.
  • A primitive expression is either a pointwise target application or one of TTL's four coordinate operations: @einsum, @gather, @scatter, or @rearrange.
  • A target operation is a pure scalar operation supplied by the consumer, such as @multiply_f32. It may be lifted pointwise over tensor operands, used as the map of an @einsum, or used as a reducer, which combines an unordered collection of mapped scalars using a declared identity.

These objects form a finite dataflow graph: a node is an input, constant, selector, or primitive result, and a directed edge means that one node consumes another node's value. The graph has no cycles:

parameters, globals, scalar literals
                 |
                 v
       primitive and selector bindings
                 |
                 v
           result references

Every reference points to a parameter, global, or earlier binding. TTL has no source-defined operation, general call expression, recursion, or compile-time control flow.

A straightforward consumer can therefore be organized as this pipeline:

source characters
    -> lexer (tokens)
    -> parser (syntax tree)
    -> name resolver
    -> type and primitive verifier
    -> interpreter or lower-level representation

A lexer recognizes the tokens in Section 2.1. A parser recognizes the grammar in Section 2.2. A name resolver connects every name use to its declaration or binding. A verifier applies the contextual rules in Sections 3 through 8. An interpreter evaluates the verified graph; a lowering compiler translates it to another representation. This organization is illustrative, not required: conformance depends on observable acceptance and semantics, not on internal compiler phases.

A first implementation need not optimize. It can store each tensor as a map from named coordinate assignments to scalar values, enumerate the finite coordinate domains described by each primitive, and materialize every binding in source order. This direct model is sufficient to implement all observable TTL semantics. Appendix A gives a compact implementation sequence.

TTL specifies values and results, not their implementation. Storage, physical layout, loops, scheduling, tiling, kernels, synchronization, devices, and host orchestration are outside the language. The graph is finite, but finiteness does not prescribe coordinate traversal, reduction grouping, or one bit pattern for approximate floating-point results.

The consumer supplies a target environment containing scalar dtypes, target signatures, target semantics, and reducer metadata. Every conforming environment implements the portable ttl.lang baseline defined in Section 6. Target names are self-identifying through their @ prefix and require no TTL declaration.

1.1 Complete introductory example

axis row := 2, shared := 3, column := 4;

global weight: f32[shared column];

export function linear(
    x: f32[row shared]
) -> f32[row column] :=
    let
        %0 = @einsum[
            row shared,
            shared column
            -> row column
        ](x, weight) map=@multiply_f32 reduce=@add_f32
    in
        %0;

The first line declares three axis identities and their extents. weight is a module input, while x is supplied on each invocation of linear. The two input patterns of @einsum describe the axes of x and weight. Equal axis names align. shared is absent from the result pattern, so it is reduced; row and column remain in the result. At every contributing coordinate the map target multiplies one element of each operand, and the reduce target adds the mapped values. %0 names the resulting tensor and is the export's result.

Sections 4 through 7 define each of these statements precisely.

2. Complete syntax

2.1 Lexical specification

Source text is Unicode, but every TTL token is ASCII. Whitespace and comments may occur between tokens and are discarded. They cannot occur within a token. // begins a line comment. /* and */ delimit a non-nesting block comment. Any non-ASCII character outside whitespace or a comment is a lexical error.

id          ::= /[A-Za-z_][A-Za-z0-9_]*/ ;
integer     ::= /0|[1-9][0-9]*/ ;
float       ::= /([0-9]+\.[0-9]*|\.[0-9]+)([eE][+-]?[0-9]+)?/
              | /[0-9]+[eE][+-]?[0-9]+/ ;
at-id       ::= /@[A-Za-z_][A-Za-z0-9_]*/ ;
perc-id     ::= /%(0|[1-9][0-9]*)/ ;
dollar-id   ::= /\$[A-Za-z_][A-Za-z0-9_]*/ ;

Text between / delimiters is a regular expression. Within it, [abc] matches one listed character, A-Z denotes a character range, juxtaposition forms a sequence, | separates alternatives, parentheses group expressions, X* and X+ mean zero-or-more and one-or-more, X? means optional, and a backslash quotes punctuation such as . or $.

at-id, perc-id, and dollar-id are each one token; whitespace cannot separate the prefix from its body. Leading zeroes are forbidden in a multi-digit integer or perc-id number. Quoted words in the syntactic grammar are reserved tokens and are not id tokens. Quoted punctuation in that grammar also denotes tokens.

2.2 Syntactic grammar

::= defines a production, | separates alternatives, adjacent terms form a sequence, and parentheses group terms. X?, X*, and X+ mean optional, zero-or-more, and one-or-more. Quoted text is literal syntax; unquoted names are nonterminals defined elsewhere in the grammar. EOF is the end of the source file.

program     ::= axis-decl* global* function+ EOF ;
axis-decl   ::= "axis" axis-definition ("," axis-definition)* ";" ;
axis-definition ::= static-axis-definition | dynamic-axis-definition ;
static-axis-definition ::= id ":=" integer ;
dynamic-axis-definition ::= dollar-id ("over" axis+)? ;
global      ::= "global" id ":" type ";" ;

function    ::= "export" "function" id
                "(" (param ("," param)*)? ")"
                "->" results ":=" expr ";" ;
param       ::= id ":" type ;
results     ::= type | "(" type ("," type)+ ")" ;
type        ::= id ("[" dimension* "]")? ;
dimension   ::= static-dimension | dynamic-dimension ;
static-dimension ::= id (":=" integer)? ;
dynamic-dimension ::= dollar-id ;

expr        ::= let-expr | id | perc-id
              | "(" (id | perc-id) ("," (id | perc-id))+ ")" ;
let-expr    ::= "let" binding (";" binding)* "in"
                (id | perc-id
                 | "(" (id | perc-id) ("," (id | perc-id))+ ")") ;
binding     ::= (id | perc-id) "="
                (literal | "-" (integer | float | "inf")
                 | (id | perc-id) selector | primitive) ;

selector    ::= "[" selection ("," selection)* "]" ;
selection   ::= id "=" integer (":" integer)? ;

primitive   ::= at-id ("[" axis-spec "]")?
                "(" (id | perc-id) ("," (id | perc-id))* ")"
                (("map" | "reduce") "=" at-id)* ;
axis-spec   ::= axis-pattern ("," axis-pattern)* "->" axis-pattern ;
axis-pattern ::= (axis | id ":=" integer | axis-product)* ;
axis-product ::= axis ":=" "[" axis ("*" axis)+ "]" ;

axis        ::= id | dollar-id ;
literal     ::= integer | float | "inf" | "true" | "false" ;

Thus an axis pattern is a sequence of only three item forms: an axis a, a static axis whose domain is defined by an extent a := N, or a one-level axis product p := [a * b * ...]. The := token defines an axis domain, either by an extent or by a product; square brackets distinguish a structural product from an extent expression, and * separates the product's ordered factors. A product has at least two factors, and each factor is only an axis, so the notation defines neither aliasing nor a recursive or nested axis structure.

The axis set denoted by a pattern contains the identity written by each bare axis or extent definition and the left-hand, parent identity of each axis product. The factors inside an axis product are relation metadata; they are not additional members of that pattern's axis set. Thus batch hidden := [head * channel] denotes {batch, hidden}, not {batch, hidden, head, channel}. Section 7.4 requires head and channel to occur on the opposite side of that rearrangement relation.

TTL distinguishes definition from binding. := defines an export body or an axis domain; = binds a local value, selector coordinate or range, or named primitive clause. The two roles do not overlap.

A primitive operand name is not necessarily a global. It may resolve to an export parameter, a global, or an earlier binding. Literals enter the flat dataflow as bindings before a primitive consumes them. For example:

let
    %0 = 2.0;
    %1 = @einsum[row, -> row](x, %0)
         map=@multiply_f32
in
    %1

Here x is an export parameter, %0 is a local scalar literal binding, and the empty second input pattern denotes its rank-zero axis set. No global is required.

An integer used as a static extent MUST be in 1 .. 2147483647. Empty patterns denote rank-zero tensors. Section 4.3 defines scalar literal ranges.

The bracketed form names one of the coordinate primitives @einsum, @gather, @scatter, and @rearrange. The unbracketed form names a target operation and is defined in Section 6.1. A direct target application has no map or reduce clause. The primitive-specific sections below further restrict patterns, operands, and clauses. A bracketed primitive contains at most one map clause and at most one reduce clause. Clause order has no meaning.

3. Static validity and names

Parsing establishes only grammatical structure. A static error is an invalid program that a consumer must reject before execution. Examples include an unresolved name, an invalid extent, a type mismatch, and an incompatible primitive axis specification. A dynamic error can be detected only for a particular invocation, such as an out-of-domain gather index. Section 8 gives the complete error requirements.

TTL uses distinct namespaces for:

  • concrete axes declared by axis;
  • dtypes and target operations supplied by the target environment;
  • exports declared by export function; and
  • tensor values: module globals and, within each export, parameters and bindings.

An axis name is resolved only in an axis position, and a dtype is resolved only at the start of a type. An at-id resolves only in the target environment. These contextual namespaces allow an axis and a tensor value to have the same id spelling without ambiguity.

Global names are distinct. Export names are distinct. Within an export, parameter and binding names are pairwise distinct and do not shadow globals. An id used as a value reference resolves to the unique parameter, earlier binding, or global of that spelling. A perc-id may name only a binding and must refer to an earlier binding. Forward references and unresolved references are static errors. Names in different exports are independent.

The grammar deliberately admits some forms that these and later contextual rules reject, including duplicate primitive clauses and an @ name used in the wrong role. Such rejection is a static error, not an alternative parse.

4. Axes and tensor types

4.1 Concrete axis identities

Every axis identity used by a TTL module MUST be declared exactly once. Repeated occurrences of the same name denote the same concrete identity; no occurrence is a generic placeholder or an alias.

A static axis is written with an id. Its declaration gives one resolved, positive integer base extent. A dynamic axis is written with a dollar-id. Its extent is supplied at invocation time and may vary with coordinates of other axes. The optional over clause declares those direct dependencies:

axis batch := 2, hidden := 4096,
     $sentence over batch, $token over $sentence;

Let parents(a) be the unordered set written after over. The strict transitive closure of parents is the semantic dependency partial order, and support(a) is the set of all predecessors of a. The graph MUST be acyclic. Declaration order has no meaning. Every parent MUST be a declared axis. A dynamic axis without over is a root.

For the declaration above:

support($sentence) = {batch}
support($token)    = {batch, $sentence}

A runtime value containing $sentence carries a length for each batch coordinate. A value containing $token carries a length for each (batch, $sentence) coordinate. For example, an invocation may supply:

length_sentence(batch=0) = 3
length_sentence(batch=1) = 2
length_token(batch=0, sentence=0) = 5

These equations describe logical domains; TTL does not prescribe their memory representation.

A bare static dimension uses its declared extent:

f32[batch hidden]

A dynamic dimension states that its domain is supplied by the runtime value:

f32[batch $sentence $token]

Its runtime descriptor carries its extent at each support coordinate. The descriptor MUST conform to the module's dependency partial order. Primitive axis patterns name only identities; their domains come from typed operands and the primitive's coordinate relation.

4.2 Tensor types and domains

A tensor type is an element dtype and a finite mapping from axis identities to coordinate domains. It is not an ordered shape:

f32[batch hidden]
f32[hidden batch]

These two spellings denote the same type. A bare static dimension uses its declared base extent. An explicit a := N gives that occurrence the positive extent N; this is the form used for a smaller, reindexed domain produced by a slice. No type contains one axis identity twice. A dynamic dimension cannot carry an inline extent.

Consequently, two values may use the same static axis identity with different local extents, for example f32[token] and f32[token := 4]. They are not the same tensor type. The shared identity says that their coordinates have the same meaning; the local domains say which coordinates each value contains.

A type is complete when its dtype is supplied by the target environment, every axis is declared, every static occurrence has a resolved positive extent, and every dynamic occurrence has declared support. Every global, parameter, and export result type MUST be complete.

For dynamic axis $a, its descriptor is a logical function from coordinate assignments over support(a) to non-negative extents. A zero extent is valid. At each support coordinate, valid $a coordinates are 0 .. length_a(s)-1.

Tensor type well-formedness is:

WF(T[A]) iff
    every axis in A is distinct, and
    for every dynamic d in A: support(d) is a subset of A

Every global, parameter, inferred binding, and result MUST satisfy WF. A runtime descriptor supplies extents, not additional dependency edges. A tensor operation cannot remove a predecessor while retaining its dependent dynamic axis.

Static type equality compares dtypes, axis identities, static extents, and the declared support of dynamic axes. At invocation time, a descriptor instantiates each dynamic domain. Whenever an operation aligns two occurrences of the same dynamic axis, their lengths MUST agree at every aligned support coordinate; otherwise invocation fails with a dynamic error.

Permuting axis entries in a type or ordinary axis pattern does not change meaning. The dependency partial order is semantic; textual enumeration order is not.

4.3 Element types

A consumer MUST provide the mandatory ttl.lang types bool, i32, f16, and f32 and may provide additional nominal dtypes. Their value domains are Boolean values, signed 32-bit two's-complement integers, IEEE 754 binary16, and IEEE 754 binary32, respectively. There is no implicit dtype conversion. Integer, floating, and Boolean literals have types i32, f32, and bool, respectively; TTL has no textual f16 literal.

A non-negative i32 literal is in 0 .. 2147483647. A negative literal is - followed by a magnitude in 1 .. 2147483648. A decimal floating literal is converted to f32 using IEEE 754 round-to-nearest, ties-to-even. Overflow and underflow follow binary32 conversion. inf and -inf denote positive and negative binary32 infinity. TTL has no textual NaN literal, although target operations and supplied values may produce NaNs.

Dtypes are nominal: two dtype occurrences are equal exactly when their names identify the same type in the target environment.

5. Modules and dataflow

5.1 Globals and exports

A global is an immutable module input with module-instance lifetime. The execution environment supplies one well-typed value for every global before an export is invoked. Globals remain direct references and are not added to export parameter lists. All invocations on one module instance observe the same global values. A host may create a different instance, but TTL defines no operation that mutates an existing instance or global.

An export has complete parameter and result types. A module contains one or more exports, and their names are distinct. Parameters retain source names. Bindings may use human names or generated names such as %10; names are unique within an export and do not shadow parameters or globals.

5.2 Bindings, constants, and results

A let is one flat, textual dataflow sequence. Each binding refers only to parameters, globals, or earlier bindings and produces one immutable value. Its type is uniquely derived from its right-hand side; no expected result type may supply missing type information. The final result contains the declared number of value references, in result order, and their inferred types equal the export result types.

A literal binding produces one rank-zero tensor. TTL has no non-scalar tensor literal. A selector binding derives its type by Section 5.3. A direct target binding derives its type by Section 6.1, and a coordinate primitive binding by Section 7. Every binding produces one value; multiple export results are several graph edges, not a tuple-valued tensor.

An export body that returns one result is a single reference. A body that returns multiple results is a parenthesized list of at least two references. Its arity and each inferred type MUST match the declared result list in the same order.

5.3 Resolved selectors

A selector operates on distinct static axes of an earlier value:

axis batch := 2, token := 8, hidden := 64;

// x: f32[batch token hidden]
x[token=3]    // f32[batch hidden]
x[token=2:6]  // f32[batch token := 4 hidden]

For a=i, 0 <= i < extent(a) and the result removes a. For a=begin:end, 0 <= begin < end <= extent(a) and the result retains a with local extent end-begin, reindexed from zero. All bounds are resolved integer literals. The resulting type MUST remain well formed; selecting away a dependency while retaining its dynamic axis is invalid. A range selection on a support axis restricts the dependent runtime descriptors to that range and reindexes their support coordinates from zero.

6. Scalar target environment

6.1 Environment interface

The consumer supplies scalar dtypes and @ operations. Every referenced target has an ordered input-dtype list, one result dtype, and pure scalar semantics. A target may report a dynamic numerical-domain error for inputs outside its stated domain. A map target receives one element from each tensor operand in operand order. TTL performs no implicit scalar conversion.

A direct target application lifts those scalar semantics pointwise:

%0 = @cast_i32_f32(count);
%1 = @add_f32(x, bias);

The application axis set is the union of its operand axis sets. Occurrences of the same named axis align and MUST have compatible domains; an operand that lacks an application axis broadcasts along it. At each application coordinate, the target receives the element selected from each operand in source operand order. The result has the target's result dtype and the application axis set. Thus a call on only rank-zero operands is itself rank zero. Axis enumeration in the result type remains non-semantic.

A direct target application MUST NOT carry an axis specification, map clause, or reduce clause. It cannot remove an axis. A call that must project or reduce coordinates uses @einsum instead.

A consumer verifies and executes a module relative to one target environment. Changing a referenced target's signature or semantics changes that environment and therefore changes the program being consumed.

6.2 Portable ttl.lang baseline

Every target environment MUST provide the following names and signatures. The arithmetic names denote their conventional scalar operations in the stated dtype. An environment MUST document rounding, exceptional values, and domain errors for approximate operations.

@subtract_f32 (f32, f32) -> f32 —
@multiply_f32 (f32, f32) -> f32 —
@divide_f32 (f32, f32) -> f32 —
@negate_f32 (f32) -> f32 —
@minimum_f32 (f32, f32) -> f32 reducer, identity positive infinity
@maximum_f32 (f32, f32) -> f32 reducer, identity negative infinity
@greater_f32 (f32, f32) -> bool —
@exp_f32 (f32) -> f32 —
@log_f32 (f32) -> f32 —

exp and exp2 compute powers of e and 2; log and log2 are their corresponding logarithms. ceil returns the least integral value not smaller than its input, represented as f32. rsqrt(x) computes 1 / sqrt(x). cast_i32_f32 converts its input to f32. Each select returns its second input when its Boolean input is true and its third input otherwise. The environment's documented floating-point rules refine these mathematical descriptions.

An environment may add nominal dtypes and target operations. Such additions do not change TTL syntax. A module is valid only relative to an environment that contains every target it references.

6.3 Reducers

A reduce target has one identity and defines the meaning of reducing a finite multiset of scalars. Reduction is invariant under permutation: TTL never exposes an ordered fold. Subtraction, division, concatenation, and any other operation whose intended result depends on input order are not reducers.

For an exact dtype, reducer r with identity e MUST form a commutative monoid over its semantic scalar domain. Concretely, it satisfies r(e, x) = r(x, e) = x, r(x, y) = r(y, x), and r(r(x, y), z) = r(x, r(y, z)). The target environment asserts these laws; a consumer need not prove them.

An approximate scalar operation, such as binary32 addition, need not be associative. For every reducer over an approximate dtype, the environment MUST instead provide an order-invariant predicate:

admissible_r(M, observed)

M is the finite multiset of semantic inputs. The predicate defines all valid observations and covers numerical error, NaNs, infinities, signed zero, overflow, and domain failure without referring to an enumeration of M. It MUST admit the declared identity for an empty multiset. For an exact dtype, the observed value is the unique commutative-monoid reduction in the target's declared scalar domain.

7. Tensor primitives

This section uses ordinary set union and set difference on axis identities. A coordinate projection keeps only the coordinates named by a specified axis subset. A multiset is an unordered collection that may contain repeated scalar values.

7.1 @einsum

An @einsum has one input axis pattern per operand and one result axis pattern:

@einsum[row shared, shared column -> row column](x, weight)
    map=@multiply_f32 reduce=@add_f32

An @einsum MUST have at least one operand. Its patterns contain only bare axes; extent definitions and axis products are invalid. The consumer checks it as follows:

  1. Input pattern i names exactly the unordered axis set of operand i.
  2. Aligned occurrences of a static axis have equal extents. Aligned dynamic occurrences satisfy Section 4.2.
  3. The iteration set I is the union of all input axis sets.
  4. The result pattern contains distinct axes drawn from I.
  5. The reduction set is K = I minus result_axes.

An operand missing an axis from I broadcasts along that axis. If map is present, its target signature is the operand dtypes in operand order and its result dtype is the mapped dtype. With one operand, an omitted map is the identity and the operand dtype is the mapped dtype. With two or more operands, map is required. TTL supplies no implicit multiplication.

If K is empty, reduce is forbidden and the result dtype is the mapped dtype. If K is nonempty, reduce is required; it names a reducer whose input and result dtype are the mapped dtype. The tensor result has the result pattern's axis domains and that dtype. TTL supplies no implicit addition.

When K is empty and map names a direct target, the expression is semantically equivalent to applying that target directly to the operands. A producer SHOULD emit the direct form because it states pointwise intent without a vacuous axis specification. In particular, a rank-zero cast is written @cast_i32_f32(x), not @einsum[ -> ](x) map=@cast_i32_f32.

For each result coordinate q, every valid assignment k to K selects one element from each operand by projecting (q, k) onto that operand's axes. The map target produces one scalar. These mapped scalars form a finite multiset M_q; the result at q is the reducer result for that multiset. An empty M_q produces the reducer identity. An exact result is its commutative-monoid reduction; an approximate result satisfies the target's admissibility predicate. No traversal or reduction order is observable.

7.2 @gather

axis batch := 2, vocabulary := 32000, token := 8;

// data: f32[batch vocabulary]
// indices: i32[batch token]
@gather[vocabulary -> token](data, indices)
// result: f32[batch token]

@gather has exactly two operands, data and indices, and no map or reduce clause. indices has dtype i32. Its axis specification contains one bare source axis s before -> and a set of bare inserted axes after it; extent definitions and products are invalid.

Let D be the data axis set, J the index axis set, and R = D minus {s}. The consumer checks:

  1. s occurs in D and not in J.
  2. Every axis in J that is not inserted occurs in R with a compatible domain.
  3. The inserted set is exactly J minus R.
  4. The inferred result type is well formed under Section 4.2.

The result has dtype(data) and axes:

(D minus {s}) union J

For each result coordinate q, project q onto J and read integer j from indices. Project q onto R, set the s coordinate to j, and read that element of data. A negative or out-of-domain j is a dynamic error.

7.3 @scatter

axis batch := 2, token := 8, vocabulary := 32000;

// base: f32[batch vocabulary]
// updates: f32[batch token]
// indices: i32[batch token]
@scatter[token -> vocabulary](base, updates, indices)
    reduce=@add_f32
// result: f32[batch vocabulary]

@scatter has exactly three operands: base, updates, and indices. It has exactly one reduce clause and no map clause. The reducer is a complete target reducer whose two input dtypes and result dtype equal the common dtype of base and updates. indices has dtype i32.

The axis specification contains one bare contribution-axis pattern before -> and exactly one bare destination axis after it. Extent definitions and axis products are invalid. Let B, U, and J be the axis sets of base, updates, and indices; let I be the contribution set; let s be the destination axis; and let R = U minus I. The consumer checks:

  1. s occurs in B and occurs in neither U nor J.
  2. I is a subset of both U and J.
  3. J is a subset of U, and J minus R = I.
  4. B minus {s} is a subset of R.
  5. Every aligned axis occurrence has a compatible domain under Section 4.2.

The result has the value dtype and axis set R union {s}. The domain of s comes from base; the domains of R come from updates. base broadcasts over retained axes it omits, and indices broadcasts over retained axes it omits. The base therefore supplies the complete destination domain, including the runtime descriptor when s is dynamic; no expected result type supplies shape information.

For result coordinate q, let C_q be the finite multiset of update values whose coordinates agree with q on R and whose index value equals q(s). The result is the reducer applied invariantly to

{ base(project(q, B)) } multiset-union C_q

according to Section 6.3. A coordinate with no matching update therefore retains its base value. Colliding updates have no writer order. With the additive reducer, a zero-valued base gives scatter-add and the value operation needed as the reverse-mode counterpart of @gather. A negative index or an index outside the destination domain at its retained coordinate is a dynamic error.

7.4 @rearrange

Every @rearrange is exactly one of the following classes. Its decomposition must be unique. It has no map or reduce clause and never inspects element values. It has one input pattern per operand. Each input pattern's denoted axis set and occurrence domains MUST equal its operand's type. The result pattern's denoted axis set and the relations below determine the result type.

A single-source coordinate map has one operand and composes disjoint local relations:

  • preserve one axis identity and domain;
  • relabel one source axis as one distinct result axis with the same domain;
  • split or merge one static parent and an ordered factor sequence declared by parent := [f1 * ... * fn];
  • remove a static extent-one source axis or insert a fresh a := 1 result axis; or
  • replicate along a fresh static result axis a := N, where N > 1.

For example, this expression splits hidden into head and channel:

axis batch := 2, hidden := 32, head := 4, channel := 8;

// x: f32[batch hidden]
@rearrange[
    batch hidden := [head * channel]
    -> batch head channel
](x)
// result: f32[batch head channel]

Every input and result axis belongs to exactly one relation, and different relations use disjoint axes. Preserved axes have equal domains. A relabel is written by one unmatched bare axis on each side, as in @rearrange[token -> source](x). The two identities remain distinct; the operation explicitly transfers coordinates and does not declare an alias. Their domains are equal. Static relabels require equal extents. Dynamic relabels require equal support sets and transfer the source descriptor under the result identity. If more than one pairing of unmatched axes satisfies these rules, the rearrangement is ambiguous and invalid.

In a product relation, the parent and factors are pairwise-distinct static axes. The parent annotation occurs on one side of ->; its factors occur as axis occurrences on the opposite side and are metadata, not additional axes on the parent's side. An extent-defined factor occurrence supplies its local extent; a bare factor occurrence uses its declared base extent. The parent extent equals the product of the factor extents. No other source axis may disappear and no other result axis may appear. For factor extents n_1 ... n_n:

extent(parent) = n_1 * ... * n_n
coord(parent) = sum(i=1..n,
                    coord(f_i) * product(j=i+1..n, n_j))

The first equation is checked statically. The second is the mixed-radix coordinate map; the last factor varies fastest. Splitting uses the equation as written, and merging uses its unique inverse. A product has at least two factors; a one-axis relation is forbidden aliasing. Changing only the written order of preserved axes is the identity. Unit insertion and removal use their only coordinate, zero. Replication reads the same source element at every coordinate of the fresh result axis. Here fresh means absent from the opposite pattern, not undeclared: every axis remains declared at module scope.

A multi-source concatenation has at least two operands. For a common axis set C, input-specific axes s_i, and fresh result axis r:

axis batch := 2, left := 3, right := 5, joined := 8;

// a: f32[batch left], b: f32[batch right]
@rearrange[batch left, batch right -> batch joined](a, b)
// result: f32[batch joined]
axes(input_i) = C union {s_i}
axes(result)  = C union {r}
extent(r, c) = sum(i, extent(s_i, c))

All operands have one common dtype. The s_i and r identities are pairwise distinct, absent from C, and either all static or all dynamic. In the static case the result extent equals the sum of the input-specific extents. In the dynamic case they have one support set, and the result descriptor is their pointwise sum. Operand order concatenates coordinates within r; it does not order tensor axes. Let offset_i(c) be the sum of the extents of s_j for operands j < i at shared support coordinate c. Result coordinate r=k reads the unique operand i satisfying offset_i(c) <= k < offset_i(c) + extent(s_i, c), at source coordinate s_i = k - offset_i(c).

@rearrange preserves the operand dtype. It does not gather, scatter, reduce, apply a scalar operation, or otherwise discard coordinates. Every result must be well formed, and no coordinate-relation provenance remains in its type.

8. Evaluation and errors

An invocation begins with one value for every global and export parameter. Those values MUST match their declared dtypes, static domains, and dynamic descriptor requirements before any result is observed.

Bindings are written in dependency order. Because values and target operations are pure, an implementation may evaluate nodes in any order that follows graph dependencies. Primitive argument order remains semantic for scalar target signatures and concatenation operand order. Tensor coordinate traversal is unobservable. A reference implementation may choose a stable traversal, but a TTL program cannot depend on it.

Exact reductions produce their unique scalar-domain value. Approximate reductions produce a value admitted by their target predicate.

8.1 Required static errors

A conforming consumer MUST reject:

  • lexical or grammatical invalidity;
  • a duplicate, unresolved, forward, or forbidden shadowing name;
  • an undeclared axis, invalid extent, cyclic dependency, or unresolved parent;
  • an ill-formed tensor type under Section 4.2;
  • an unknown target or incompatible target signature;
  • an invalid primitive name, arity, axis pattern, clause, or inferred type;
  • a binding whose dependencies are not earlier values; and
  • export result arity or type disagreement.

8.2 Required dynamic errors

An invocation fails dynamically on:

  • a supplied value that violates a dynamic descriptor requirement;
  • incompatible lengths for aligned occurrences of one dynamic axis;
  • a negative or out-of-domain gather or scatter index; or
  • a scalar target numerical-domain failure.

Silent positional matching, renaming, truncation, padding, wrapping, or clamping is forbidden unless an explicit target operation defines it.

9. Conformance

A producer of TTL MUST emit resolved concrete axis declarations, including the dynamic-axis dependency partial order, complete globals and export signatures, valid primitive coordinate relations, fixed scalar target references, and explicit result edges. Runtime values supply conforming dynamic descriptors. No consumer-side specialization or compile-time evaluation may be required to interpret the emitted module.

An implementation may provide parsing, verification, interpretation, lowering, or any stated combination. Each implemented part MUST obey this manual and identify the target environment used.

The language boundary permits small, independently testable implementation stages: tokenize and parse the complete grammar; resolve names and construct axis/type tables; verify bindings and infer their types; then interpret or lower the verified finite graph. This is implementation guidance, not a separate language profile or course requirement.

TTL 0.1 artifacts remain governed by their released manual and paired target environment. This specification makes no compatibility claim that would reinterpret a TTL 0.1 artifact.

Appendix A. Minimal implementation guide (non-normative)

This appendix suggests one small architecture. It adds no language rules.

  1. Tokenize and parse. Preserve source locations on syntax nodes so later errors can name the offending declaration or expression. Do not perform type inference in the parser.
  2. Build module tables. Record axes, globals, exports, dtypes, and target signatures. Reject duplicate declarations. Compute the transitive support set of every dynamic axis while detecting dependency cycles.
  3. Represent a type directly. A useful representation is (dtype, {axis_identity: domain}); do not use an ordered tuple of extents as semantic type identity. An implementation may retain written order for diagnostics or host-data decoding, but type equality ignores it.
  4. Verify each export topologically. Seed a value table with globals and parameters. For each binding, resolve its operands, apply the selector or primitive rule in Sections 5 and 7, and record the uniquely inferred result type. Finally compare the referenced result types with the declared export results.
  5. Interpret by coordinates. Represent a coordinate as a map from axis identity to integer. Implement @einsum by projection and finite-domain enumeration, @gather by replacing one coordinate, @scatter by grouping updates at their indexed destination, selectors by restriction and reindexing, and @rearrange by its explicit coordinate relation.
  6. Separate static and dynamic failures. Reject invalid graphs before an invocation. Check supplied shapes, segment descriptors, gather and scatter indices, and scalar numerical domains while evaluating a particular invocation.

A useful first conformance ladder is: scalar identity; elementwise unary map; broadcast binary map; one-axis reduction; matrix multiplication; scalar and range selection; gather; scatter with and without collisions; split/merge rearrangement; concatenation; and a dynamic-axis example. At each rung, test both the inferred tensor type and the coordinate values, plus at least one required rejection.
