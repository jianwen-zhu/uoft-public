YTL Language Reference Manual

Version 0.1

Status and normative language

This document is the normative definition of YTL 0.1. It specifies source syntax, static semantics, reference semantics, and the required relationship between YTL and TTL.

The key words MUST, MUST NOT, REQUIRED, SHALL, SHALL NOT, SHOULD, SHOULD NOT, MAY, and OPTIONAL are to be interpreted as described by RFC 2119 and RFC 8174 when, and only when, they appear in bold.

Examples are normative when introduced by a requirement and otherwise illustrative. Text outside this manual does not extend the language.

1. Scope

YTL is a first-order functional tensor language. A YTL program describes immutable tensor values, named-axis relationships, structural specialization, and compositions of compiler-owned tensor primitives.

YTL defines logical values and results. It does not define physical storage, buffer allocation, tiling, kernel boundaries, scheduling, device placement, checkpoint formats, tokenization, or host orchestration.

Every conforming YTL program MUST elaborate to a finite TTL program. Elaboration may remove source abstraction and sugar but MUST NOT change the program's reference result.

YTL 0.1 admits:

  • dense and segmented tensors;
  • ordinary and structurally recursive first-order functions;
  • compile-time static parameters and conditionals;
  • restricted multiple results;
  • named-axis scalar lifting and @einsum;
  • static subviews, @gather, and @rearrange; and
  • the portable scalar vocabulary selected by import ttl.lang;.

Anything not admitted by this manual is not YTL 0.1.

2. Lexical structure

Source text is Unicode, but every token defined by YTL 0.1 is ASCII. Whitespace separates tokens and is otherwise insignificant.

YTL recognizes line and non-nesting block comments:

// through the end of the line
/* through the next closing delimiter */

An unterminated block comment is invalid.

id      ::= /[A-Za-z_][A-Za-z0-9_]*/ ;
integer ::= /0|[1-9][0-9]*/ ;
float   ::= /([0-9]+\.[0-9]*|\.[0-9]+)([eE][+-]?[0-9]+)?/
          | /[0-9]+[eE][+-]?[0-9]+/ ;
target  ::= "@" id ;
core-id ::= "%" integer ;
module-name ::= id ("." id)* ;

Leading zeroes are forbidden in a multi-digit integer. A negative numeric literal consists of the token - followed by an unsigned literal.

3. Complete grammar

X?, X*, and X+ mean optional, zero-or-more, and one-or-more respectively. Alternatives are separated by |. Literal punctuation is quoted.

literal    ::= integer | float | "true" | "false" ;
dtype      ::= id ;
binary-op  ::= "||" | "&&" | "==" | "!=" | "<" | "<=" | ">" | ">="
             | "+" | "-" | "*" | "/" | "**" ;
operator   ::= binary-op | "!" ;

program    ::= import* function* EOF ;
import     ::= "import" module-name ";" ;
function   ::= marker* "function" name static-params? "(" params? ")"
               ("->" results)? function-clause* ("=" expr)? ";" ;
static-params ::= "[" id ("," id)* "]" ;
marker     ::= "export" | "reducer" | "target" ;
function-clause ::= "identity" "=" expr | "contract" "=" contract ;
contract   ::= "associative" | "reassociative" | "left_ordered" ;
params     ::= param ("," param)* ;
param      ::= id (":" type)? ;
type       ::= dtype ("[" dimension* "]")? ;
dimension  ::= axis ("=" expr)? ;
axis       ::= id | "$" id ;
results    ::= type | "(" type ("," type)+ ")" ;
name       ::= id | operator | target ;
reference  ::= id | operator | target ;
scalar-name ::= id | operator ;

binding    ::= value-name "=" expr | "(" id ("," id)+ ")" "=" expr ;
expr       ::= "let" binding (";" binding)* "in" expr
             | "if" expr "then" expr "else" expr
             | prefix ((binary-op | inner-product-op) prefix)* ;
inner-product-op ::= scalar-name "." scalar-name "[" axis+ "]" ;
prefix     ::= ("-" | "!") prefix | primary ;
primary    ::= atom selector* ;
atom       ::= literal | value-name
             | id static-args? "(" args? ")" | primitive
             | "(" expr ")" | "(" expr ("," expr)+ ")" ;
selector   ::= "[" selection ("," selection)* "]" ;
selection  ::= axis "=" expr (":" expr)? ;
static-args ::= "[" expr ("," expr)* "]" ;
args       ::= expr ("," expr)* ;
value-name ::= id | core-id ;

primitive  ::= target ("[" specification "]")?
               "(" args? ")" primitive-clause* ;
specification ::= pattern ("," pattern)* "->" pattern ;
pattern    ::= term* ;
term       ::= axis | axis "=" "(" factor+ ")" ;
factor     ::= axis ("=" integer)? ;
primitive-clause ::= ("map" | "reduce") "=" reference ;

Binary operators except ** are left-associative; ** is right-associative. Precedence from lowest to highest is ||; &&; == !=; < <= > >=; + -; * /; **. Prefix - and ! bind more tightly than binary operators. An inner-product operator has the precedence of * and / and is non-associative; chained inner products require parentheses.

All compiler primitives use one call envelope:

@name[input-patterns -> result-pattern](arguments) clauses

Primitive-specific arity and pattern restrictions are static semantics, not separate grammar.

4. Programs, imports, and namespaces

A program contains imports followed by function declarations and definitions. Imports MUST precede functions. Duplicate imports are invalid.

YTL defines the portable standard module ttl.lang. It selects the scalar declarations in Section 12. Every conforming target environment MUST implement its target ABI. An implementation MUST reject an unknown import.

The following namespaces are distinct:

  • function names;
  • static parameters;
  • tensor and scalar value parameters and local bindings;
  • axes local to a function specialization; and
  • compiler-owned target names beginning with @.

A local binding MUST NOT shadow any visible value parameter, static parameter, or earlier binding. Names introduced together by a destructuring binding MUST be distinct. Parameters in one function MUST be unique. Axis names in one tensor type MUST be unique.

Names of the form %N are reserved for elaboration output. They are valid YTL tokens so TTL remains a syntactic subset, but an application source module MUST NOT define them. TTL assigns their exact binding rules.

A static parameter MUST NOT have the same spelling as an unprefixed axis in that function. This prevents ambiguity when either name occurs in a static expression.

Function names may be overloaded as specified in Section 7. Compiler-owned target names cannot be defined by an application program.

Markers on one function MUST be unique. target cannot be combined with another marker. Reducer metadata is forbidden without the reducer marker.

5. Types and tensor values

5.1 Element types

An element type is a nominal identifier. YTL itself does not close the set of element-type names; TTL therefore preserves every source dtype exactly. The mandatory ttl.lang environment defines these portable baseline types:

Type Values
bool false and true
i32 signed integers in [-2^31, 2^31-1]
f16 IEEE-754 binary16 values
f32 IEEE-754 binary32 values

A target environment MAY add types such as integer widths, bf16, f64, or low-precision floating formats. It MUST define their value domain, canonicalization, and target semantics. Distinct dtype spellings are distinct types, and there is no implicit promotion.

Integer literals have type i32, floating literals have type f32, and Boolean literals have type bool. YTL 0.1 has no textual f16 literal.

5.2 Tensor types

A tensor type consists of an element type and an ordered sequence of distinct named axes. A type without axes is a rank-zero tensor.

f32
f32[row column]
f32[batch $token hidden]

Axis identity is determined by name within one specialized function. Equal extents do not align differently named axes. Function-local axis names are alpha-renamed during call resolution; they are not nominal global types.

5.3 Static axes and extent constraints

An unprefixed axis is static. Its extent is a positive integer known during elaboration. A bare static axis obtains its extent from specialization context. An axis constraint writes a compile-time expression:

f32[row=4 column=2 * width]

The expression is a constraint, not a new dimension declaration. After the surrounding specialization binds all names, its value MUST equal the tensor's inferred extent and lie in 1..2147483647.

Every static axis that reaches TTL MUST have one concrete extent.

5.4 Dynamic axes

A $-prefixed axis is dynamic. Its runtime length may vary with the complete coordinate prefix preceding that axis. If axes are (a0, ..., an-1), a dynamic axis ak carries a logical length function:

L_ak : Coord(a0, ..., ak-1) -> non-negative integer

This function is part of the tensor value. It does not prescribe a physical segmented representation.

The coordinate set is constructed from left to right. A static axis of extent N extends every prefix by 0..N-1; a dynamic axis extends prefix p by 0..L_axis(p)-1. Empty dynamic segments are valid.

Two occurrences of the same dynamic axis are compatible when:

  1. equal prefix domains have exactly equal lengths;
  2. a less-specific prefix domain covers every refined segment and supplies a capacity at least as large as each refined length; and
  3. the result domain can project its prefix to at least one contributing descriptor.

Compatible candidates derive a result length by pointwise minimum. A primitive may impose stronger descriptor rules.

6. Static expressions and structural specialization

Static parameters are declared after a function name and supplied after a call name:

function layers[n](x: f32[token hidden]) -> f32[token hidden] = ...;
layers[12](x)

A static parameter denotes a non-negative i32 value during elaboration. A static expression may contain integer and Boolean literals, static names, parentheses, and these operations:

Operand kind Operations
integer +, -, *, **, <, <=, >, >=, ==, !=
Boolean !, &&, `

An exponent MUST be non-negative. Equality operands MUST have the same kind. Division is not available in a static expression.

An if whose condition depends on a static parameter is a structural conditional. Elaboration evaluates the condition and elaborates only the selected branch.

Recursive calls are permitted only within a cycle of functions that all have the same nonzero static arity. On every recursive edge:

  • each static argument MUST be the corresponding static parameter or that parameter minus a positive integer literal; and
  • at least one argument MUST strictly decrease.

No recursive call may depend on a tensor value. A recursive specialization that would produce a negative static argument is invalid. These rules require elaboration to terminate and remove all recursion before TTL.

7. Functions, calls, and reducers

7.1 Ordinary functions

An ordinary function is first-order: it is not a runtime value and cannot be stored in a tensor. A function definition MUST have a body. Calls are resolved statically and inlined during elaboration.

A helper value parameter without an annotation takes the complete type of its corresponding argument separately in each resolved call specialization. A helper without a result annotation takes the type of its elaborated body. Such omissions do not participate in dispatch: if typed and untyped overloads both match, the call is ambiguous. Exported functions MUST declare complete parameter and result types.

7.2 Exported functions

The export marker identifies an externally invocable root. A program may define multiple exports. Export names MUST be unique.

An exported function MUST have a body, complete value-parameter types, and one or more complete result types. YTL 0.1 exports MUST NOT declare static parameters; ordinary helpers perform all structural specialization before the export boundary.

7.3 Overload resolution and axis matching

Functions may share a name. A candidate is applicable when value arity, static arity, element types, ranks, and repeated local-axis relationships match the arguments. A typed parameter requires the same element type and rank. Its distinct local axes map bijectively to distinct argument axes, and every repeated local axis must map consistently across all parameters. The spelling of a local axis has no nominal significance. An untyped parameter imposes no type constraint. Result types do not participate in candidate selection.

Exactly one candidate MUST be applicable. Zero candidates or multiple candidates are static errors. Declaration order MUST NOT break an ambiguity.

7.4 Reducers

A reducer is a scalar function marked reducer. It MUST:

  • have exactly two parameters of one rank-zero element type;
  • return that same element type;
  • define one signed scalar literal of that type as its identity;
  • declare one contract; and
  • have a scalar body.

A reducer body may contain literals, its parameters, ordinary scalar calls, target scalar calls, scalar operators, scalar let, and scalar if. It MUST NOT contain tensor primitives, subviews, tuples, structural calls, or free values. The literal restriction makes the identity directly available to TTL verification without interpreting an arbitrary source expression.

The contracts have these meanings:

Contract Permitted evaluation
left_ordered the specified left fold only
reassociative any parenthesization preserving leaf order
associative any parenthesization preserving leaf order, under the reducer's asserted exact associativity

No contract permits permutation of reduction leaves.

7.5 Target declarations

A target function @name(...) -> type; declaration names a compiler-owned rank-zero operation. It has no YTL body. Application programs obtain target declarations through an import; they MUST NOT redeclare them.

8. Expressions

8.1 Bindings

A let expression evaluates one or more bindings in textual order and then evaluates its body:

let
    a = f(x);
    b = g(a)
in
    b

Each binding is immutable and visible only to later bindings and the body.

8.2 Multiple results

A parenthesized list of two or more result types and values denotes restricted multiple results:

function pair(x: f32) -> (f32, f32) = (x, x);
let (left, right) = pair(x) in left

Multiple results may appear only in a function result signature, the returned expression, and a destructuring binding. They are not tuple tensors or first-class tuple values. Nesting and indexing are forbidden.

8.3 Operators and scalar lifting

An operator expression is an ordinary call to the corresponding operator function. If no tensor overload matches a call but exactly one scalar overload matches the argument element types, the scalar function is lifted over the union of the arguments' named axes. Missing axes broadcast by name.

There is no implicit element-type conversion during lifting.

8.4 APL-style inner products

An inner-product expression combines a reducer and a mapper using APL's reducer.mapper order:

left +.*[shared] right
left minimum.+[shared] right

It has exactly two operands. The name to the left of . MUST resolve to a dyadic scalar function marked reducer; the name to the right MUST resolve to a dyadic scalar function. Resolution uses the operand element types and the mapper result type. These references are compile-time operator parameters, not first-class function values.

Both operands are elaborated and typed independently of the surrounding expected type. Let L and R be their ordered axes, and let SL and SR be the respective subsequences containing only axes shared by both operands. SL and SR MUST be identical. Thus this abbreviated form cannot conceal a disagreement in shared-axis order; an explicit @einsum is required in that case.

The bracket MUST contain one or more distinct axes, each occurring in both operands. Its order MUST equal the order of those axes in the common shared subsequence. Let K be the contracted axes. The iteration axes I are the ordered union of L and R, preserving first occurrence from L and then R, and the result axes O are I with every axis in K removed, preserving order. No result annotation or surrounding expression participates in this inference. The expression is exactly equivalent to:

@einsum[L, R -> O](left, right) map=mapper reduce=reducer

where L, R, and O stand for the corresponding concrete patterns, not literal axis names. Consequently the expression denotes one einsum; it does not first materialize left mapper right. All @einsum extent, dynamic descriptor, identity, reduction-order, and result-type rules apply.

For example, if query has axes batch head token channel and key has axes batch head source channel, then:

query +.*[channel] key

is equivalent to:

@einsum[
    batch head token channel,
    batch head source channel
    -> batch head token source
](query, key)

The ordinary @einsum form remains the form for unary or n-ary operations, explicit result ordering, and reductions whose axes are not shared by both operands. An inner product never implies a rearrangement.

8.5 Value conditionals

An if not controlled by static parameters is eager tensor selection. The condition MUST have element type bool. Both alternatives are evaluated, must have one element type, and must describe the same result domain. The condition may broadcast over that domain but cannot select a shape.

8.6 Static subviews

A selector may index or slice one or more static axes:

x[layer=1]
x[row=1:3, column=0]

Selector expressions MUST be compile-time integers. For source extent N, an index i requires 0 <= i < N and removes its axis. A range [begin:end] requires 0 <= begin < end <= N, retains the axis, and gives it extent end - begin. Selecting a dynamic axis is invalid.

9. Tensor primitive envelope

A primitive name begins with @. A bracketed specification contains one pattern per operand followed by one result pattern. Spaces separate axes; commas separate operand patterns.

Every primitive operand is evaluated before the primitive. Primitive clauses are compile-time scalar references. Duplicate clauses are invalid. Sections 10 and 11 define the admitted primitive names and constraints.

10. @einsum

An einsum has one bare-axis input pattern per operand and one bare-axis result pattern:

@einsum[row shared, shared column -> row column](a, b)

Input pattern i MUST exactly match operand i's ordered axes. The result pattern MUST contain distinct axes drawn from the ordered union of input axes. Equal static axes require equal extents; dynamic occurrences require compatible descriptors.

The iteration axes are the ordered union of input axes, preserving first occurrence. Axes absent from the result are reduced. Each operand is projected from an iteration coordinate by its pattern; missing axes broadcast.

The optional map clause names a scalar function or target receiving one element from each operand. If omitted, one operand maps identically and two or more operands use a left-associated *.

A reduce clause names a reducer. If reduced axes exist and the clause is omitted, + is selected. A reduce clause is forbidden when no axis is reduced.

For each result coordinate, mapped values are ordered lexicographically by the iteration axes. Reduction begins with the selected identity. Empty reduction groups therefore produce the identity. The reducer contract controls legal reassociation.

11. Structural tensor primitives

11.1 @gather

@gather[source-axis -> inserted-axes](data, indices)

indices MUST have element type i32. The source side names exactly one axis of data. Let R be the data axes after removing that source axis. The inserted axes are exactly the index axes absent from R, in index order. Other index axes are shared with R.

The result replaces the data source axis with the inserted axes. For each result coordinate, the projected index value selects the source-axis coordinate. A negative or out-of-domain index is a dynamic error.

11.2 Single-source @rearrange

A single-source rearrange is a value-independent bijection formed from axis permutation, static split/merge, rename, and insertion or removal of extent-one logical axes.

@rearrange[hidden=(head channel) -> head channel](x)

A bare term is one logical axis. A composite term physical=(a b ... z) states that physical is the row-major product of its logical factors, with the last factor varying fastest. Factor extents are inferred from surrounding tensor types and any explicit factor=N annotations. The solution MUST be unique and every static product MUST match its physical extent.

Every non-unit logical input coordinate MUST occur exactly once in the output and conversely. A dynamic axis may only remain unfactored in YTL 0.1.

Splitting uses mixed-radix row-major coordinates. Merging (i0, ..., ik) with extents (N0, ..., Nk) computes:

(((i0 * N1 + i1) * N2 + i2) ... * Nk + ik)

11.3 Multi-source @rearrange

With two or more operands, rearrange performs ordered composition along one axis position:

@rearrange[
    batch $past channel,
    batch $step channel
    -> batch $source channel
](past, step)

All terms MUST be bare. Inputs and result have equal rank and one element type. Exactly one position changes axis name; all other positions agree in name and domain. Static lengths sum. Dynamic segments concatenate in operand order independently at every prefix coordinate. Empty segments are valid.

@gather and @rearrange accept no map or reduce clause.

The import also supplies +, binary and unary -, *, /, minimum, maximum, >, exp, log, log2, exp2, ceil, rsqrt, the three f32 conversions, f8e4m3fn(f32), and f4e2m1(f32). +, minimum, and maximum are reducers with the identities and contracts defined by the imported vocabulary.

Every target call MUST match one signature exactly. Floating target results are rounded once to their declared format. @divide_f32 requires a nonzero divisor; @log_f32, @log2_f32, and @rsqrt_f32 require a positive input. f8e4m3fn is finite E4M3 with maximum magnitude 448 and round-to-nearest, ties-to-even. f4e2m1 has magnitudes {0, 0.5, 1, 1.5, 2, 3, 4, 6} and resolves exact midpoints toward the smaller magnitude. Both casts saturate at their maximum finite magnitude. Inputs or intermediate results outside the finite numerical domain are dynamic errors in YTL 0.1.

Every conforming target environment MUST implement these signatures, scalar semantics, reducer identities, contracts, and descriptor behavior. Environments may add targets without changing YTL or TTL.

13. Elaboration to TTL

For each requested export specialization, elaboration MUST:

  1. resolve imports and overloads;
  2. bind and verify static extents and parameters;
  3. alpha-rename function-local axes;
  4. evaluate structural conditionals and unfold structural recursion;
  5. inline ordinary functions and scalar helpers;
  6. make lifting, projections, conversions, maps, and reducers explicit;
  7. split compound scalar expressions into target-atomic tensor bindings;
  8. resolve selector bounds and rearrange factor extents; and
  9. emit a finite, fully typed TTL export.

One source module may elaborate several exports into one TTL module. Source imports are resolved during step 1 and MUST NOT appear in the TTL module. Every emitted @target reference is resolved against the target environment selected by the source imports. That same environment is an explicit input to subsequent TTL verification, execution, or lowering.

The emitted text MUST satisfy the TTL Language Reference Manual. Every valid TTL program is also valid YTL source syntax. TTL introduces no delimiter, call envelope, or declaration form absent from YTL.

TTL is the official post-elaboration semantics of YTL. The type and dynamic descriptor of every elaborated source expression MUST equal the type and descriptor of its emitted TTL graph. The TTL rules are therefore the exact definition of descriptor propagation through source primitives; elaboration may not resolve, discard, pad, or flatten a dynamic axis merely because a particular invocation supplies concrete data.

14. Evaluation and errors

Bindings and function arguments are evaluated from left to right. Tensor coordinates use lexicographic axis order. Values are immutable. An implementation may choose another execution schedule only when it preserves the result and all reducer-contract restrictions.

A conforming implementation MUST diagnose:

  • lexical or grammatical invalidity;
  • unresolved or ambiguous calls;
  • unbound or duplicate names;
  • invalid static expressions or nonterminating structural call patterns;
  • unsatisfied extent constraints;
  • incompatible static extents or dynamic descriptors;
  • primitive arity, pattern, clause, or type errors;
  • invalid selector bounds;
  • out-of-domain gather indices; and
  • scalar numerical-domain violations.

Silent truncation, padding, wrapping, clamping, or undefined behavior is forbidden unless a target operation explicitly defines it.

15. Conformance

YTL conformance has four independent parts:

  1. syntax conformance: accepting exactly the admitted grammar;
  2. static conformance: enforcing all typing, extent, structural, and primitive constraints;
  3. elaboration conformance: producing semantically equivalent valid TTL YTL; and
  4. execution conformance: matching the reference value and permitted numerical ordering.

An implementation MUST state which parts it provides. Acceptance of syntax without successful static checking does not make a program conforming.

16. Complete example

import ttl.lang;

function layer[n](
    x: f32[token hidden],
    weights: f32[layer hidden output]
) -> f32[token hidden] =
    let
        weight = weights[layer=n];
        projected = @einsum[
            token hidden, hidden output -> token output
        ](x, weight)
    in
        @rearrange[token output -> token hidden=(output)](projected);

function layers[n](
    x: f32[token hidden],
    weights: f32[layer hidden output]
) -> f32[token hidden] =
    if n == 0 then
        x
    else
        layers[n - 1](layer[n - 1](x, weights), weights);

export function model(
    x: f32[token=4 hidden=8],
    weights: f32[layer=2 hidden=8 output=8]
) -> f32[token=4 hidden=8] =
    layers[2](x, weights);

The rearrange renames the equal-width projection axis back to hidden, making the block compositional. The recursive call count is controlled only by the static parameter n; elaboration emits a finite primitive graph.
